# 単GPUの費用・締切・並行実行を分ける資源資格案

2026-10-30。**PROPOSED / NOT EXECUTED**。本書を登録しても新MD・学習・推論・LOFは承認されない。現在は文書のみ。物理・学習配方の採択と共有資源の許可を得てから、独立した実行カードを凍結する。

## 1. 問いと測定対象

1×RTX PRO 6000 Blackwell Max-Q 96GBで、MDを一時停止して更新する機会費用は何秒か。更新後の成果が締切までに利用可能になるか。CPU/GPU並行が必要で有益か。この順で確認する。GPU使用率だけから資源競合を認定しない。

旧B1では4 ns MD子process平均209.5531秒、追加学習4.2464秒、推論4.2532秒、学習内部fit約0.8449秒だった。[元費用と定義](../P1-B1-Expansion/cost-and-runtime.md)。これらは異なる階層の計時であり、差を全てGPU切替時間としない。LOFがどの原処理に含まれるかを静的に確認し、次の計測では独立区間を設ける。学習費用を大きく見せるために歩数・入力数を増やさない。

## 2. R0単独費用の固定行列候補

既知r01-S4を工程入力として事前指定する。正確な原task/model/pool ID・SHA・seed・依存ソフト版は承認カードに列挙する。N1で有利な枝やL2で良いseedを選ばない。下表は5種×3反復=15処理単位であり、方策効果実験ではない。

|処理|固定入力・量の候補|主に分ける時間|
|---|---|---|
|MD単独|最初の既定r01-S4の座標・準備を固定、元4 nsレシピ。新しい独立出力、同じ工程seedで3回|起動/準備、context初期化、積分、DCD/log保存、終了|
|追加学習単独|同状態の既定M0-200のmodel/optimizer/RNGを毎回復元、同じ200追加歩・batch4・固定データ|読込、device移動、fit、validation、checkpoint公開|
|推論単独|同一の保存modelとFULL候補、既存GPU経路を固定|load、host/device転送、前向、embedding保存|
|LOF単独|同一の保存embedding、FULLの元規則・順序。GPU不可視|読込、fit、score、順位・Top1公開|
|データ準備/I/O単独|同一の既存MDと固定品質/入力変換。GPU不可視|読込、特徴生成、整形、保存・可視化可能化|

三回は独立科学標本ではなく同入力の工程反復。初回と二回目以降を個別報告し、OS cacheを強制消去しない。GPU clock/電力設定や共用driverを変更しない。p95などの安定した裾分位を3回から推定しない。S8/最大候補への費用外挿は別資格と明記し、この15単位を無断で増やさない。

候補保護値：全R0 wall1,800秒、単工程300秒で再確認停止、単worker/数値thread1、process-tree RSS2GiB、VRAM8GiB、追加出力2GiB。MDを含むため、これは**新GPU計算の別承認が必要**。予算内でも全15単位で終了し、残時間を追加計算へ転用しない。最初の単位が超過すれば入力を小さくして通すのではなく、原因と必要枠を審査する。

## 3. 時計と利用可能時刻

各runに単調時計`monotonic_ns`の起点t0とJST対応を記録する。`submit → process_start → input_ready → compute_start/end → output_flush → quality_ready → atomic_publish → consumer_visible`を別eventとする。科学評価は読み取り可能かつ固定品質判定が完了した`available`時刻だけで決める。親の時刻と子の時刻は同じ時計の校正を確認する。

科学指標はオフライン計算できるが、方策にはnative RMSD/Qを渡さない。保存されたframeがHより前のMD時刻を持っていても、品質と出力の公開がHを越えればH内成果には入れない。MDの物理時間[ns]と実時間[s]を別列にする。

最初は**既定chunk終了後の一括公開**を候補とし、chunk長はR0/時間尺度資格後に凍結する。streamingを使うなら公開chunk、flush、品質、再開の同値性を別に検証し、都合よい途中frameだけを使わない。締切到達後の安全保存・cleanup時間は`tail_s`として費用記録するが、成果期限を延長しない。

同じ残時間判定を全方策に適用する。完了費用の保守的推定＋事前固定marginを超える仕事は新規受理しない。marginやfallbackは校正後・未知結果開封前に登録する。締切直前に始めたAIが間に合わない事実も失敗として残す。失敗・再試行・復元はt0をリセットせず課金する。

## 4. 費用の非重複な記録

主費用はt0から締切/終了までの実時間。内訳はMD、学習、推論、LOF、prep、転送、起動、待機、失敗、復元、結果公開、tail。ネストしたfitとprocess全時間を足さず、親子spanと排他的区間を別表にする。並行区間は和ではなく区間のunionを使う。

GPU指定processの生存秒、kernel活動、全GPU利用率、CPU process-tree秒、予約待ち、実験全体経過は別量。利用率は観測間隔・GPU UUID・process所有者と共に保存し、他者の負荷が混入した場合は明示する。他者の負荷を作ったり停止したりしない。

固定入力・生成物のSHA、環境/driver/library、seed、CPU affinity/thread、GPU UUID/割当、キャッシュ状態の観測可能な範囲を記録する。内部host/IPや他学生の情報は公開表へ転載しない。GitHubに小型表/manifest、原軌跡/重みは許可サーバに置く。

## 5. 並行実行は独立の門

R0が完了しても並行試験を自動開始しない。まずMDとAIの両方に実時間上の余地があり、必要VRAM/RSSが余裕内、共有GPU利用の調整が明確な場合だけ提案する。

候補は(A) MD+CPU LOF/prep、(B) MD+GPU学習、(C) MD+GPU推論。CPU競合も無害とは仮定しない。各組で同じ固定仕事量の逐次区間と並行区間を対応させ、開始順を事前固定/均衡化し、3工程反復案を別予算にする。単位task slowdownと両仕事の完了makespan、公開遅延、メモリ、失敗を報告する。並行時の浮動小数/速度差は科学的同値性を保証しない。

MIG/MPS、新stream priority、system設定の変更は含めない。GPU単独でも更新費が小さく、並行の追加利益が費用/複雑性に見合わない可能性を残す。並行資格がなければ、C/B2はGPU逐次・明示課金だけで成立する設計にする。

## 6. 中止・交付

セッション開始時と各資源消費単位の前にCPU/RAM/GPU/所有者/予約を確認。他者占有、権限不明、SHA/親/RNG不整合、OOM・非有限、保護値超過で停止。成功単位を上書きしない。VPN接続失敗なら研究者に知らせ、別経路探索をしない。

交付は15単位の個別費用、event trace、原SHA、不成功/未実施、利用可能時刻の検証、厳格deadline人工試験、600秒/代替Hの**実測に基づく**実行可能量。費用資格PASSは科学成果の十分性でもC/B2の承認でもない。今回の審査では実行0/15、並行0件である。
